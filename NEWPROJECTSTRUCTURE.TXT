TORCHAT — DOCZELOWA STRUKTURA PROJEKTU I PLAN MIGRACJI
========================================================

Status dokumentu: plan architektoniczny
Zakres: monorepo, granice odpowiedzialnosci, nazewnictwo, migracja i cleanup.
Poza zakresem: zmiana zachowania produktu, zmiana protokolu kryptograficznego,
automatyczne przenoszenie plikow bez osobnego review.


0. CEL
-------

TorChat ma byc monorepo z trzema jasno oddzielonymi produktami:

  1. klientem urzadzenia (tozsamosc, SQLCipher, MLS, P2P onion, pairing),
  2. aplikacjami platformowymi (Android i Windows/desktop),
  3. efemerycznym relayem rendezvous do pairingu.

Najwazniejsza zasada produktu pozostaje niezmienna:

  URZADZENIA SA ZRODLEM PRAWDY.

Relay nie jest backendem aplikacji. Nie przechowuje kontaktow, wiadomosci,
profili ani historii. Jest krotkotrwalym, slepym brokerem pairingu.

Docelowa struktura ma umozliwiac szybka odpowiedz na pytania:

  - gdzie lezy kod domenowy?
  - gdzie lezy lokalny storage?
  - gdzie lezy P2P?
  - gdzie lezy protokol wire?
  - gdzie lezy relay?
  - co jest tylko Androidem, tylko Windowsem albo wspolnym UI?
  - co mozna usunac jako cache, fixture, legacy albo build output?

2. DIAGNOZA PROBLEMU STRUKTURALNEGO
----------------------------------

2.1. Nazwa ./mobile/ jest mylaca

Katalog ./mobile/ jest faktycznie wspolna aplikacja Flutterowa, a nie tylko
klientem mobilnym. Zawiera rowniez Windows, Linux, macOS oraz UI desktopowe:

  ./mobile/windows/
  ./mobile/lib/windows_runtime.dart
  ./mobile/lib/features/shell/desktop/
  ./mobile/lib/app/desktop_notification_service.dart
  ./mobile/lib/app/desktop_window_lifecycle.dart

Jest to poprawne technicznie dla Fluttera, ale mylace semantycznie. Programista
moze zalozyc, ze desktop jest wylacznie w ./desktop/, mimo ze UI desktopowe jest
w ./mobile/.

2.2. ./desktop/ nie jest cala aplikacja desktopowa

./desktop/ jest natywnym hostem Rust. Odpowiada za proces desktopowy, Tor,
sekrety, blokade pojedynczej instancji i most do engine. Nie jest wlascicielem
calego UI. Flutter UI jest obecnie w ./mobile/.

2.3. Granica relay/client jest za slaba

Typy relay i rendezvous znajduja sie w ./common/torchat-core/src/. Wspolne typy
protokolu sa dobre, ale implementacja serwera nie powinna zyc w crate'cie core
klienta. Relay musi byc wlasnoscia ./services/torchat-relay/.

2.4. torchat-client-engine ma za szeroka odpowiedzialnosc

Jeden crate zawiera runtime actor, transport peer, relay client, storage,
SQLite/SQLCipher, SQL oraz publiczne API. Jest to miejsce, w ktorym latwo
powstaja cykliczne zaleznosci i niejasne granice.

2.5. W skryptach istnieje ryzyko duplikacji

./scripts/modules/ jest obecnym publicznym pipeline deploy/build.
./scripts/internal/ zawiera rowniez build logic. Nie moga istniec dwie
rownorzedne implementacje tych samych decyzji: target ABI, staging, cache,
device resolution, reset danych i deployment.

6. DOCELOWY FLOW APLIKACJI
--------------------------

6.1. Aplikacja Android

  apps/mobile/flutter
       -> packages/torchat-flutter-ui
       -> packages/torchat-client-engine-ffi
       -> packages/torchat-client-engine
       -> runtime + storage + peer + rendezvous client

  apps/desktop/flutter
       -> packages/torchat-flutter-ui
       -> desktop platform adapter
       -> apps/desktop/native
       -> packages/torchat-client-engine

6.3. Pairing

  UI
   -> client engine
   -> rendezvous client
   -> services/torchat-relay
   -> rendezvous client drugiego urzadzenia
   -> client engine drugiego urzadzenia

6.4. Zwykla wiadomosc

  UI
   -> client engine
   -> durable local outbox SQLCipher
   -> torchat-peer onion P2P
   -> durable local storage odbiorcy
   -> P2P receipt

Relay nie wystepuje na tej sciezce.

11. KRYTERIA "STRUKTURA JEST GOTOWA"

Projekt mozna uznac za uporzadkowany, gdy wszystkie ponizsze sa prawdziwe:

  [ ] Jednoznacznie wiadomo, gdzie jest Android app, desktop app i shared UI.
  [ ] Relay jest samodzielnym service i nie zalezy od client storage/runtime.
  [ ] Tylko protocol crates sa wspoldzielone przez relay i client.
  [ ] Engine jest facade, a nie workiem na storage/peer/relay/actor.
  [ ] Zwykle wiadomosci maja tylko P2P transport.
  [ ] Deploy ma jeden publiczny entrypoint i jedna decyzje ABI.
  [ ] Nie ma rownoleglych v2/legacy/dead-code paths bez uzasadnienia.
  [ ] Build/cache directories nie sa commitowane.
  [ ] Kazdy katalog ma README albo oczywista odpowiedzialnosc.
