# Torca 0.2 Release Checklist

This checklist applies to every Torca 0.2 beta, release candidate and stable
build distributed outside the development team. The Windows installer is built
separately, but it must package the exact validated Windows release directory
and preserve the hashes produced by this process.

## 1. Freeze the candidate

- Update `release/version.json`.
- Synchronize Cargo and Flutter versions with
  `scripts/release/check-release-version.ps1`.
- Commit every source, migration, dependency-lock and documentation change.
- Do not reuse a build number or update-manifest key identifier.
- Record the candidate commit and stop accepting unrelated changes.

## 2. Prepare update signing

- Store the Ed25519 private key outside the repository and application profile.
- Back up the private key offline.
- Export the corresponding raw 32-byte public key as base64.
- Select a stable, unique key identifier.
- Confirm that the public key and key identifier supplied to the release command
  are the same values expected by the generated manifest.
- Never copy the private update-signing key into a Flutter define, artifact or
  release report.

## 3. Build the candidate

Run platform validation to create the exact artifacts used during manual tests:

```powershell
.\scripts\release\validate-torca-release.ps1 `
  -Target all `
  -RequirePlatforms `
  -BuildAndroidBundle `
  -UpdateKeyId torca-update-2026-01 `
  -UpdatePublicKey <BASE64_ED25519_PUBLIC_KEY>
```

The command must complete without failed or skipped required steps. Manual tests
must use these signed release artifacts, never debug builds.

## 4. Record manual evidence

Create the evidence template after the candidate commit is frozen:

```powershell
.\scripts\release\new-manual-evidence.ps1
```

For every item:

- keep the exact test id;
- record the tester;
- record actual run count and soak duration;
- add UTC start/completion timestamps;
- reference logs, screen recordings, screenshots or sanitized diagnostics;
- mark `passed` only when the full matrix description is satisfied;
- describe every anomaly, even when it did not reproduce again.

Validate the completed file:

```powershell
.\scripts\release\check-manual-evidence.ps1 `
  -EvidencePath .\.torca\release\0.2.0-beta.1\manual-evidence.json
```

## 5. Produce release artifacts

Use the canonical command. It reruns policy and platform validation, requires the
completed manual evidence, collects artifacts, generates SBOM/checksums and signs
the update manifest:

```powershell
.\scripts\release\release-torca.ps1 `
  -Target all `
  -BuildAndroidBundle `
  -ArtifactBaseUrl https://downloads.example.invalid/torca/0.2.0-beta.1 `
  -SigningPrivateKey X:\offline\torca-update-ed25519.pem `
  -SigningKeyId torca-update-2026-01 `
  -UpdatePublicKey <BASE64_ED25519_PUBLIC_KEY> `
  -ManualEvidencePath .\.torca\release\0.2.0-beta.1\manual-evidence.json `
  -ReleaseNotesUrl https://example.invalid/torca/releases/0.2.0-beta.1
```

## 6. Verify the output

Required output:

- Android signed APK;
- Android signed AAB when requested;
- Windows release bundle ZIP for the separately built installer;
- legal notices;
- release matrix report;
- manual-evidence receipt;
- CycloneDX SBOM;
- Flutter package inventory;
- SHA-256 checksum report;
- signed update manifest.

Independently verify:

- artifact hashes match the checksum report and update manifest;
- the update manifest verifies with the public key embedded in the clients;
- APK/AAB signing identity matches the expected release certificate;
- the Windows installer contains the unmodified validated release bundle;
- version, build, channel and commit are visible in both applications;
- diagnostics export remains local and sanitized;
- no development identities, local endpoints or signing secrets are present.

## 7. Go/no-go

Do not distribute when any of the following is true:

- known data loss, identity reset or key disclosure;
- pairing can become permanently stuck;
- a message can be silently lost or duplicated in the UI;
- upgrade from the previous distributed build has not been tested;
- required manual evidence is missing;
- a required platform step is skipped;
- release artifacts were rebuilt after manual validation;
- release signing or update signing identity is uncertain;
- diagnostic privacy scanning failed;
- the release commit differs from the report or evidence.

## 8. Publish and monitor

- Publish release notes and known issues before sending artifacts.
- Publish checksums, SBOM and source tag with the artifacts.
- Keep the signed update manifest immutable for that version.
- Start with a small tester group and record every report against the exact
  version/build/commit.
- Withdraw the manifest immediately if a blocker is discovered.
- Follow `upgrade-and-rollback.md` for migration or rollback decisions.
